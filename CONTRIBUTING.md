# Contributing to inhousecode

Thanks for considering a contribution — this project is early, and feedback
shapes it more than anything else right now.

By participating, you're expected to follow the
[Code of Conduct](CODE_OF_CONDUCT.md).

## Before you start

- Read [AGENTS.md](AGENTS.md) for the project's invariants. Several
  behaviors — like the review agent never getting write access, or every
  repair loop being bounded — are load-bearing, not stylistic. A PR that
  breaks one of them won't be merged even if it "works."
- For anything beyond a small fix, open an issue first to align on approach
  before you invest time in an implementation.

## Reporting bugs / suggesting features

Open an issue. Include, where relevant:

- What you expected vs. what happened
- Your OS, and the output of `inhousecode doctor`
- The command you ran, and the relevant part of its output

## Making changes

1. Fork the repo and create a branch from `main`.
2. Keep the change focused — one concern per PR.
3. If you're adding a config key, touch the schema, the default, and
   [docs/configuration.md](docs/configuration.md) together — keep them in
   sync (`config/review.config.schema.json`,
   `config/review.config.default.json`, `lib/config.py`'s `INTEGER_BOUNDS`).
4. Guidance meant for *every* code-touching agent belongs in
   `craft_standard()` in `lib/copilot.sh`, not duplicated into an individual
   prompt.
5. Run the static checks and, where applicable, the manual acceptance path in
   [docs/testing.md](docs/testing.md) before opening the PR:

   ```bash
   for f in bin/inhousecode lib/*.sh hooks/*.sh install.sh; do
     bash -n "$f" || echo "SYNTAX-FAIL $f"
   done
   python -m py_compile lib/*.py
   ```

6. Write commit messages that explain *why*, not just what.

## Opening the PR

- Describe what changed and why, and link the issue it addresses if there is
  one.
- Note any invariant from [AGENTS.md](AGENTS.md) your change touches and how
  you preserved it.
- Expect review focused on correctness and on whether the change keeps the
  tool's guarantees intact — this is a review gate, so we hold its own code to
  the standard it enforces on everyone else's.

## Project conventions

- Bash for orchestration, Python 3 for anything parsing JSON. No other
  runtime.
- Magic values are named constants grouped at the top of the file.
- Shell variables derived from config are `INHOUSECODE_<SECTION>_<KEY>` in
  upper snake case, generated by `lib/config.py`.

## Questions

Not sure where something belongs, or whether an idea fits the project? Open an
issue and ask — that's a welcome use of the tracker, not a burden on it.
